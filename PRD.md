# PRD: Jev в oh my pi

Дата: 2026-10-07. Статус: требования для обсуждения; выбор реализации остаётся открытым. [S:U3]

## 1. Цель

Пользователь задаёт задачу верхнеуровнево и получает максимально корректный результат с минимальными затратами. [S:U2]

Продукт должен компенсировать проблемы дешёвых моделей через умного судью Jev и готовый тулсет в omp. [S:U1] [S:U2]

## 1.1 Роли и полномочия

Пользователь задаёт целевую иерархию ролей: "я заказчик / jev это архитектор/лид / основная модель это ведущий исполнитель / а таск агенты это работяги". [S:U5]

В этой иерархии основная модель должна все свои важные решения валидировать через Jev. [S:U5]

Предлагаемый рабочий ритм - много дешёвых итераций: главная модель выносит важные решения и все ревью кода на Jev через фиксированный набор вариантов, получает ответ и повторяет цикл. [S:U5]

Требование иерархии и обязательной валидации - желание пользователя. Способность Jev в этой роли лучше основной модели - гипотеза, она не подтверждена сравнением; см. [ASM:1] и раздел 10. [S:U5] [ASM:1]

Состав "важных решений" - какие классы решений обязательны для валидации, а какие нет - пользователь не определил. [GAP:3]

## 2. Проблема и контекст

Пользователь работает в oh my pi с DeepSeek v4.1 Flash из-за скорости и низкой цены. [S:U1]

По наблюдениям пользователя, модель делает лишнее, неверно понимает запросы, бросает задачи и плохо реализует решения. [S:U1]

У пользователя также есть GLM5.3, но его скорость не устраивает. [S:U1]

Jev предполагается использовать для оценки понимания задачи, направления работы и полноты результата через заранее заданные варианты решений. [S:U1]

Дополнительные сценарии охватывают маршрутизацию скиллов и моделей, классификацию задач и планирование через выбор нужных топиков. [S:U3]

## 3. Ожидаемый результат и критерии успеха

| Цель пользователя | Что потребуется проверить | Основание |
| --- | --- | --- |
| Модель правильно понимает задачу | Соответствие результата исходному запросу | [S:U1] |
| Модель делает только нужное | Наличие изменений за пределами запроса | [S:U1] |
| Модель завершает задачу | Выполнение требуемого объёма, а не только сообщение о завершении | [S:U1] |
| Модель правильно реализует решение | Проверки поведения, соответствующие конкретной задаче | [S:U1] [GAP:1] |
| Работа обходится дёшево | Полная стоимость задачи с учётом судьи и повторных попыток | [S:U2] [GAP:1] |
| Работа сохраняет приемлемую скорость | Полное время до результата с учётом проверок | [S:U1] [GAP:1] |

Численные цели и набор задач для сравнения ещё предстоит согласовать. [GAP:1]

## 4. Требования

Таблица фиксирует желаемое поведение продукта, а не подтверждённые возможности Jev. [S:U1] [S:U3] [S:JEV]

| Требование | Условие и требуемое поведение | Основание |
| --- | --- | --- |
| FR-01 | Когда пользователь даёт задачу, система должна через Jev определить её тип: разработка, аналитика, запрос. | [S:U3] |
| FR-02 | Когда система подбирает скиллы для задачи, она должна использовать оценку Jev. | [S:U3] |
| FR-03 | Когда система выбирает модель для работы, она должна использовать оценку Jev. | [S:U3] |
| FR-04 | Когда система составляет план разработки, она должна через Jev выбрать относящиеся к задаче топики из заранее подготовленного списка. | [S:U3] |
| FR-05 | Когда система оценивает понимание задачи исполнителем, она должна через Jev различать правильное, неполное и неверное понимание. | [S:U1] |
| FR-06 | Когда система оценивает ход работы, она должна через Jev проверить соответствие направления исходной задаче. | [S:U1] |
| FR-07 | Когда исполнитель объявляет завершение, система должна через Jev оценить полноту результата. | [S:U1] |
| FR-08 | Когда система получает оценку судьи, она должна получить решение из заранее заданного набора вариантов. | [S:U1] |
| FR-09 | Когда исполнитель решает задачу, система должна предоставить ему готовый тулсет для этой работы. | [S:U2] [GAP:2] |
| FR-10 | Когда основная модель принимает важное решение или завершает ревью кода, она должна выносить его на Jev через заранее заданный набор вариантов и действовать по ответу. | [S:U5] [GAP:3] |
| FR-11 | Когда основная модель ставит работу таск-агентам, она должна валидировать через Jev постановку и приёмку их результата. Предлагаемая политика, не утверждённое пользователем требование; входит в состав открытого вопроса об обязательных проверках. | [S:U5] [GAP:3] |
| FR-12 | Когда результат неудовлетворителен, система должна повторять дешёвые итерации исполнитель-Jev. | [S:U5] [GAP:1] |
| FR-13 | Когда проект проходит рефакторинг, система должна через Jev по заранее подготовленному каталогу проверять сохранение работоспособности старых функций; пользователь привёл пример, где после рефакторинга сохранилось порядка 20% прежних возможностей. | [S:U5] [GAP:2] |
| FR-14 | Когда агент начал общение с Jev, он должен получать замечания и возвращаться в работу в рамках той же сессии исполнителя, пока агент не завершил задачу или не начал галлюцинировать. Кэш важен только для основной и таск-LLM исполнителя: та же сессия, стабильный префикс промпта, попадание в кэш провайдера - которое не гарантировано и требует совпадающего стабильного префикса и поддержки провайдером. Кэширование вызовов к Jev в требование не входит. | [S:U6] [S:U8] [GAP:6] |
| FR-15 | Когда агент готовит вызов Jev, он должен передавать структурированный ввод: прямые цитаты из запроса пользователя, спеки и задачи; цитаты кода или результатов выполнения; выдержки логов; цитаты официальной документации со ссылками. Ответ должен быть решением из фиксированных вариантов с обоснованием. | [S:U6] [GAP:2] |
| FR-16 | Когда система принимает результат исполнителя, она должна проверять соответствие исходной задаче по подтверждающим материалам (цитаты кода, выполнение, логи, документация), а не полагаться на отчёт исполнителя; внешне убедительный отчёт или сообщение об успешном завершении сам по себе не подтверждает правильность результата. Продукт снижает этот риск, но не устраняет его полностью. | [S:U7] [GAP:3] |

Моменты обязательного вызова судьи, реакция на отрицательный вердикт и правила повторных попыток ещё не выбраны. [GAP:3]

### Планирование через топики

Пользователь предлагает заранее подготовить большие списки топиков по темам и поручить Jev разметку действительно нужных пунктов. [S:U3]

В приведённом пользователем примере система распознаёт ETL-процесс и рассматривает необходимость шардирования. [S:U3]

Требование состоит в выборе применимых топиков; обязательное шардирование для каждого ETL-процесса пользователь не задавал. [S:U3]

Форма каталога, связи между топиками и переход от выбранных топиков к архитектуре остаются открытыми. [GAP:4]

### Подготовка ввода для судьи

Пользователь предлагает небольшой скрипт: агент записывает аргументы, скрипт собирает из них понятный ввод для Jev с вариантами одобрить/не одобрить. [S:U6]

Точные поля вызова не определены. Рабочий проект состава ввода: происхождение каждого утверждения (кто и где сказал); дословные цитаты запроса, спеки и задачи; цитаты кода и результатов выполнения; выдержки логов; ссылки на официальную документацию; набор фиксированных вариантов; ожидаемая форма ответа с обоснованием. Этот состав - предложение для обсуждения, а не утверждённое соглашение. [S:U6] [GAP:2]

## 5. Путь пользователя

1. Пользователь формулирует верхнеуровневую задачу в omp. [S:U2]
2. Система использует Jev для определения типа задачи. [S:U3]
3. Система использует Jev для подбора скиллов и модели. [S:U3]
4. Для разработки система отбирает нужные топики при подготовке плана. [S:U3]
5. Исполнитель выполняет работу с готовым тулсетом; Jev оценивает понимание и направление. [S:U1] [S:U2]
6. Перед выдачей результата система оценивает полноту выполнения. [S:U1] [S:U2]

Порядок подбора модели, скиллов и топиков требует уточнения; этот сценарий не задаёт техническую последовательность вызовов. [GAP:4]

Ветви при неполном запросе, неверном плане, незавершённой работе и недоступном судье остаются открытыми. [GAP:3]

## 6. Основа для переиспользования

### harden-plan

Существующий скилл выбирает доминирующий тип задачи из 16 категорий, загружает соответствующий набор требований и ошибок, затем требует улучшить план по этому набору. [S:HARDEN]

Скилл формулирует цель так: "so even a weaker model reasons like a specialist". [S:HARDEN]

Пользователь предлагает поручить Jev решения, которые в таком подходе принимает LLM. [S:U4]

Перенос классификации и оценки по готовым спискам в Jev рассматривается как гипотеза; превосходство Jev над текущим исполнением скилла не установлено. [ASM:1]

Текущий выбор одного доминирующего типа и предложенный пользователем выбор множества топиков отличаются; правила их совмещения ещё не определены. [S:HARDEN] [S:U3] [GAP:4]

Возможности Jev закрывают часть ролей скилла, но не все. Классификация задачи из 16 категорий, маршрутизация скиллов и моделей, вердикт-гейты ревью и выбор нескольких топиков выполнимы через Choice, Noul и параллельные вопросы одного запроса. Генерация текста - вопросы adversarial-интервью, собранный совет, проект архитектуры, объяснение ревью - для Jev недоступна: она может только гейтить, ветвить и оценивать готовый текст, автор остаётся за основной моделью. [S:API] [S:JEVDEC]

### API Jev - подтверждённая механика

Endpoint `POST https://api.typesafe.ai/v1/systemone`, заголовок Bearer, тело `{state, model, questions}`; ответ содержит по одному ответу на каждый вопрос и расход токенов; модель по умолчанию `jev-latest` (фактически jev-1.13.0). Все вопросы одного запроса оцениваются параллельно и независимо от одного состояния. [S:API]

Три типа вопросов: Noul - вероятность да/нет без поля уверенности; Choice - выбор из набора до 255 вариантов с распределением вероятностей и уверенностью; Score - оценка по шкале из 2-10 уровней. [S:API]

Уверенность Choice и Score вычисляется из разброса распределения вероятностей, а не из калибровки по правильности ответов. [S:CONF]

Цену и задержку (0.042 доллара за миллион входных токенов, выход бесплатный; 70-500 мс) заявляет вендор; независимого измерения в этой работе нет, а пользователь относит стоимость Jev к пренебрежимой [ASM:3]. [S:JEVDEC]

### Интеграционная возможность в omp - проверено по исходному коду

Установленный omp 18.6.3 принимает манифесты `pkg.omp` и `pkg.pi`, устанавливает плагины через `omp plugin install <npm>` (это npm-установка в каталог плагинов) и подгружает расширения из каталогов `.omp/extensions/` и `.pi/extensions/`. [S:OMPSRC]

Расширения omp дают все замеченные точки для роли судьи: блокировка или правка вызова инструмента (`tool_call`), проверка результата (`tool_result`), продолжение вместо преждевременного завершения (`session_stop`, только расширения), маршрутизация до старта агента и в точке создания таск-агента (`before_subagent_spawn`), персистентное состояние через `appendEntry`, переживающее компакцию. Хуки дают то же, кроме `session_stop` и событий провайдера. [S:OMPSRC]

`pi-warden` из исходников совместим по манифесту и разрешению импортов: omp ремапит scope `earendil-works` на свои хост-пакеты. Фактический запуск `pi-warden` на omp в этой работе не выполнялся; расхождение поверхности событий Pi 0.85-0.87 с omp 18.6.3 не проверено. [S:OMPSRC] [S:WARDEN] [GAP:5]

Собственная реализация выглядит реалистичной как расширение omp с `tool_call`, `session_stop`, `before_subagent_spawn` и `appendEntry`. [S:OMPSRC]

### Жизненный цикл агента и кэш префикса в omp

По исходному коду omp 18.6.3: IRC-сообщение паркующемуся агенту оживляет тот же файл сессии; незанятому - открывает реальный ход в существующей сессии; работающему - доставляется как aside на границе шага. Возобновление после перезапуска восстанавливает из файла только разговор и модель; инструменты, системный промпт и схема ответа пересобираются из записи `session_init`. Новый спавн задачи - новый файл сессии; изолированные запуски возобновить нельзя. [S:OMPSRC]

Платформа осознанно держит стабильный префикс (системный промпт, тулсет, история): побочные ходы omp прямо описаны как использующие кэш промпта основного разговора. Попадание в кэш провайдера у возобновлённой сессии, TTL кэша провайдера и влияние компакции, смены тулсета или модели на префикс не проверены. Смена провайдера у таск-агента создаёт отдельное пространство кэша. [S:OMPSRC]

Следствие для FR-14: продолжение работы в той же сессии агента сохраняет условия для переиспользования стабильного префикса на уровне omp, но попадание в кэш провайдера остаётся гипотезой до измерения на реальном маршруте. [S:OMPSRC] [ASM:2]

### pi-warden как источник измерений и паттернов

`pi-warden` заявляет проверки правил, заглушек, повторяющихся ошибок и завершения без проверок: "sends it back to prove it". [S:WARDEN]

Автор `pi-warden` оставил оценки отклонения от запроса и плана без активного вмешательства по умолчанию из-за результатов собственных проверок. [S:WARDEN]

Измерения автора `pi-warden` на своём корпусе: ниже уверенности 0.8 судья ошибался в 15% вызовов, выше 0.8 - менее чем в 1%; при значении intent-скор 36 из 37 стиров пришлось бы на вызовы, запрошенные пользователем, поэтому контроль отклонения от задачи переведён в режим только записи. Это измерения автора на своих данных, а не универсальная характеристика Jev. [S:WARDEN]

Эти же данные показывают границы механизма фиксированных вариантов: неверно составленный вопрос или неполный набор кандидатов даёт уверенный, но неверный вердикт. [S:WARDEN]

`pi-classifier-router` заявляет выбор модели через Jev или Laya и поддержку "pi and Oh My Pi (omp)". Заявление подтверждено только по описанию репозитория: 0 звёзд, активность до 2026-09-23, реализации на omp не проверялись. [S:ROUTER] [S:OMPSRC]

Выбор между переиспользованием этих расширений и собственной реализацией не сделан; совместимость `pi-warden` с omp в этой работе не проверялась. [GAP:5]

## 7. Ограничения и границы

TypeSafe описывает Jev как механизм типизированных решений: "Jev gives up string generation". [S:JEV]

Произвольный текст архитектуры или плана поэтому требует отдельного механизма; кто составляет этот текст по выбранным топикам, ещё не решено. [S:JEV] [GAP:4]

Гарантия соответствия схеме ответа не доказывает правильность выбора архитектуры или полноту выполненной задачи. [S:JEV]

Этот PRD не закрепляет смену основной модели, замену omp или установку найденных расширений. [S:U3] [GAP:5]

РЕШЕНО [S:U9i]: канал - официальный прямой TypeSafe API, ключ через `pass token/jev` или переменную окружения/secret-команду; OpenRouter не используется (историческая справка: первоначальная проба OpenRouter давала 403, после предоставления пользователем официального ключа вопрос закрыт). [Закрывает GAP:6.]

### Историческая справка о пробе доступа - 2026-10-07 (устарела, сохранена для протокола)

Первоначальная проба не прошла: OpenRouter возвращал HTTP 403, `api.typesafe.ai` - сброс TLS-соединения. [S:PROBE] Статус UNVERIFIED устарел: раздел 12.4 фиксирует живой доступ через официальный ключ (HTTP 200, jev-1.13.0).

Ответ системы при отказе судьи, низкой уверенности или недоступности сети не определён; это же закрывает политику повтора итераций. [GAP:3]

Стоимость итерационного цикла (много дешёвых проходов исполнитель-Jev) не измерена; пользователь относит цену вызовов Jev к пренебрежимой [ASM:3], суммарный эффект на стоимость задачи не проверялся. [GAP:1]

Состав каталогов, тулсета и набор вердиктов предстоит уточнить; документ фиксирует их назначение. [GAP:2] [GAP:3] [GAP:4]

## 14. Курс-чек как ядро продукта (2026-10-07, коррекция курса пользователем) [S:U10]

Ядром продукта становится цикл курс-чека: исполнитель периодически и на границах (план/шаг/завершение) подаёт через jev_decision текущее действие, дословные цитаты требований и доказательства прогресса; судья отвечает проверкой дрейфа (Noul по каждому требованию: всё ещё на курсе) и выбором следующего действия из фиксированного набора [continue, return_to_requirement, replan, ask_user, verify_before_proceeding].
